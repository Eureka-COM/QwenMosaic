## 1. 論文の比べ方（Memory Mosaics at scale、§4・付録 C、公式 README）

- 比べる相手は llama 型の Transformer（RoPE）。層の数・幅・ヘッド数は Memory Mosaics v2 と同じ。データ・文脈の長さ・最適化の設定も同じで、ハイパーパラメータは Transformer に合わせて調整し、Memory Mosaics には調整し直さずに使う
- 違いは、注意の場所に v2 の記憶（短い記憶と長い記憶、位置の符号なし、学習中は長い記憶の飛ばす数をランダムに）が入ること。FFN（持続の記憶）は同じ
- パラメータ数はそろえていない（大きいモデルで 99 億対 88 億）
- 文書ごとのマスクを使う（付録 C）
- 公式 README：比べる相手は同じコードと同じデータで学習するので、比べると記憶の違いだけが出る

公式の `transformer.yaml` は新しい論文（Open-world AI）用で、関連文書を並べたデータと「行全体を読む」範囲になっている。`memory_mosaics_v2.yaml` は普通に並べたデータと「文書ごとに区切る」範囲。そのまま並べると記憶以外の条件も違うので、ここでは両方とも「普通に並べたデータ・文書ごとに区切る」にそろえる。

| 項目 | 値 | 理由 |

| 最適化 | AdamW（0.9, 0.95）、重みの減衰 0.1、勾配の上限 1、5% の立ち上げのあと余弦で 1% まで（付録 C と公式の設定） | 論文どおり |

## 3. 測るもの

学習の 0・1・2.5・5・7.5・10 割の時点で、両方について：

1. **学習に使わない文章の損失**：3 つ目のファイルの 4,096 トークン × 32 行
2. **文書の中での損失の下がり方**：3 つ目のファイルの 4,097 トークン以上の文書 128 本（それぞれ先頭から 2,049 トークン、1 本を 1 行）。位置ごとの損失（1〜16、17〜64、65〜256、257〜1,024、1,025〜2,048）と、文書ごとに early（50〜100 番目）・late（1,000〜2,000 番目）
3. **想起**：「The access code for <名前> is <5 桁>.」を文書の中に置き、32・512・1,500・3,500 トークン後に同じ言い回しを続けたとき、5 桁を正しく続けられるか（各 20 問、1 本を 1 行）

両方とも同じ文書・同じ問題で測る。比べ方（`scripts/scratch_compare.py`）：文書ごとに対にして、
- E ＝ early(MM) − early(TF)、L ＝ late(MM) − late(TF)、D ＝ E − L（文書の奥へ進むほど、Memory Mosaics の差がどれだけ縮むか。正なら Memory Mosaics のほうが前の文脈から多く得ている）
- 95% 区間はブートストラップ（文書 128 本、1 万回）

D を主な物差しにするのは、出発点（early）の違いをそのまま差し引けるから（手順 2 の G は、出発点の悪さと重なって読めなかった）。

## 4. 進め方と判定の基準

**準備（`mq-scratch-setup`）**：データを用意 → 2 本を並べて 2,000 万トークンずつ回し、速さ・VRAM・温度を測る → 学習率を決める。

- ここで決めること：本番の終わる時刻の見込み。VRAM が 2 本で 26 GB を超える、または温度が 85 ℃ を超えるなら、1 ステップの行数を減らす（4 行 → 2 行、積み上げ 4 → 8）
- 本番の学習量（12 億）は、速さが見込みの半分以下（2 本で 2 日を超える）なら研究者に聞く

**本番（`mq-scratch-main`）の途中の確認**（1・2.5・5・7.5 割）：

| 条件 | すること |
|---|---|
| NaN、前の確認点から学習に使わない損失が下がっていない、温度 85 ℃ 超、VRAM 30 GB 超 | すぐ止める（保存してから止まる） |
| 2.5 割の時点で、損失の差（MM − TF）が 0.30 を超え、5 割の時点でその差がさらに開いている | 止めて報告する（論文では普通の評価で両者は同等なので、大きな差は作り方の誤りを疑う） |
| それ以外 | 続ける。確認点ごとに損失の差・D・想起を研究者に報告する |

**最後（10 割）の判定**：

| 判定 | 条件 |
|---|---|
| 文脈の奥で上回った | L の 95% 区間の上端が 0 未満（文書の 1,000〜2,000 番目で Memory Mosaics のほうが損失が低い） |
| 文脈からより多く学ぶ | 上でなく、D の 95% 区間の下端が 0 より大きい |
| 差なし | D の 95% 区間が 0 を含む |
| Transformer のほうが文脈から学ぶ | D の 95% 区間の上端が 0 未満 |

- 学習に使わない文章の損失の差が 0.10 を超えて Memory Mosaics が悪いときは、「全体では劣る」を併記する
- 想起は距離ごとの正答率を並べて報告する（判定には使わない）
- この結果で本線をどう変えるか（最初から学習する道を本線にするか、変換の作り方を論文側に寄せるか）は、研究者が決める

## 5. 費用と時間（見込み。準備の実測で置き換える）

- 5090 で 2 本並列、使用率 7 割：12 億トークンずつで 9〜11 時間（未計測の概算）
- VRAM：1 本 5〜8 GB、2 本で 10〜16 GB（未計測の概算）
- Colab のユニット・Modal は使わない

### 準備の実測（2026-11-14 01:03〜、5090、使用率 7 割の設定）

| 項目 | 実測 |
|---|---|
| データ | 3.0 分。学習用 15.0 億トークン（文書 131 万本）、学習に使わない行 200 万トークン、長い文書 256 本（足りた） |
| 速さ（2 本並列） | Memory Mosaics 1.30〜1.34 万トークン/秒、Transformer 3.65〜3.79 万トークン/秒 |
| 速さ（Memory Mosaics だけ） | 2.32〜2.34 万トークン/秒（Transformer が終わったあと） |
| VRAM | 1 本の確保の最大は 4.5 GB（MM）・4.35 GB（TF）。nvidia-smi の合計（Windows の画面の分を含む）は 2 本で 14.7 GB、MM だけで 8.0 GB |
| 温度・電力 | 57〜66 ℃、約 344 W |
| 漏れ平均 | 公式の CUDA の部品がそのまま組み上がった（sm_120） |
| 0 割の評価 | MM 0.51 分、TF 0.26 分 |

- Memory Mosaics は Transformer の約 2.9 倍遅い（並列のとき）。記憶が短い記憶 4 ＋ 長い記憶 4 ヘッドで、読む回数が Transformer の 2 倍あり、漏れ平均の計算も加わるため
- **2 本を並べると、使用率 7 割にならない**：1 本ずつ 7 割に抑えても、片方が待つ間にもう片方が計算するので、GPU は休まない。学習率の 2 本（Transformer どうし）を並べたときの nvidia-smi の使用率は 97%（370 W、67 ℃）。1 本だけなら 66%
- そこで本番は、2 本が 1 つの鍵のファイル（`/content/gpu.lock`）で GPU を順番に使い、1 ステップの計算のあとの待ち（計算の 3/7）も順番を持ったまま取る（`scripts/scratch_train.py --gpu-lock`）。GPU 全体の使用率が 7 割になる。計算の中身は変わらない（同じ行・同じ順・同じ式）
- 本番の見込み（順番に使う形）：1 ステップの計算は MM 1.97 秒、TF 0.92 秒（上の実測から）。1 巡 ＝（1.97 ＋ 0.92）÷ 0.7 ≒ 4.2 秒で両方が 1 ステップずつ進むので、2 本は同じ速さ（約 1.57 万トークン/秒）でそろって進む。12 億トークンまでだと約 21 時間（評価と保存を足して 21.5 時間ほど）。順番にしない形（約 18 時間、うち 9 時間は使用率ほぼ 100%）より 3.5 時間ほど長いが、研究者の指示（長時間のフル稼働を避ける）に合わせる
- 見込みの 9〜11 時間（§5 の初めの概算）は、Memory Mosaics と Transformer がほぼ同じ速さだと置いた数字だった。実際は Memory Mosaics が約 2.9 倍遅い
- **学習量を 4 億に変えた**。研究者の指示（原文）：「流石に長すぎない？ 日中でとりあえず見れるって話じゃなかった？」。選べる形（3 億・4 億・6 億・12 億、使用率 7 割）を並べ、研究者が「4 億ずつ・18:30 ごろ」を選んだ。学習率の決め方・確認点の割合・判定の基準は変えない（学習率の立ち上げと余弦の下げ方は 4 億に合わせて縮む）
- 4 億での見込み：4e8 ÷ 1.57 万 ≒ 7.1 時間（評価を足して約 7.2 時間）。確認点は開始から 1 割 ≒ 0.7 時間、2.5 割 ≒ 1.8 時間、5 割 ≒ 3.5 時間、7.5 割 ≒ 5.3 時間、10 割 ≒ 7.2 時間
- VRAM・温度は基準（26 GB、85 ℃）を大きく下回るので、行数は変えない
- 確認点は 2 本がほぼ同時に通る
- 準備のうち学習率の 3 本（約 50 分）は、この直しの前に始まっていたので、並べたまま（使用率ほぼ 100%）で終える
- 参考（判定には使わない）：速さを測った 2 本は同じ設定・同じ行なので、同じ歩数で損失を並べられる。立ち上げの途中（180 歩、1,180 万トークン）で MM 6.417、TF 6.739
- 保存先（GitHub の Release）へ送るのに失敗しても学習は止めない（記録して再試行し、重みは手元の disk に残る）ように `scripts/scratch_train.py` を直した（本番の前）
